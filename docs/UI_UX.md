# UI and UX direction

The UI is **code-first and component-oriented PySide6**. Handwritten Python defines widget composition and structural layout through `QVBoxLayout`, `QHBoxLayout`, `QGridLayout`, `QFormLayout`, or `QStackedLayout` as appropriate. QSS defines appearance and widget states, not structure. Do not use fixed coordinates for ordinary screens; layouts and size policies must accommodate resizing, longer text, display scaling, Windows, and Linux.

Prefer small, composable `QWidget` subclasses with clear inputs and signals over monolithic screens, deep inheritance, or access to unrelated global state. Reusable components and top-level views should be introduced only when real screens need them. A small shared metrics module may hold spacing, margins, icon sizes, and other layout values that cannot reasonably live in QSS. Keep it small; avoid scattered magic numbers and a premature theming framework. Use application-level or component-level QSS selectors and semantic dynamic properties for colors, typography, borders, and hover, selected, disabled, and focus states. Avoid scattered widget-specific `setStyleSheet()` calls.

The planned main window has discovered games/saves in a sidebar and stacked Overview, game editor, Backups, and Raw Diff/inspection views. Navigation should preserve unrelated presentation state. The selected Ryujinx root should be shown in user-facing terms, with identification confidence when metadata is incomplete. Unknown games remain inspectable and backup-capable once safety services exist; a plugin is needed for game-specific edits. This is a direction, not a requirement for the current screen. The current UI lets users choose a root and browse unidentified save containers and diagnostics; it has no editor or write actions.

The UI expresses intent and presents results. It must not traverse Ryujinx directories or parse, mutate, checksum, back up, or replace save files inside widgets. The intended write flow is UI typed request → application service validation → mandatory verified backup and transaction → plugin transformation → typed result → UI feedback. A failed backup stops the write with no override. Game-specific plugin widgets may understand game concepts, but they use the same service boundary; generic UI remains game-agnostic. Optional artwork is loaded separately from parsing and falls back to text, generic icons, or placeholders.

Qt Designer is allowed for a specific screen with a documented benefit, but `.ui` files and generated `ui_*.py` wrappers are not the default architecture. Core behavior must remain testable without constructing `QApplication`. Focused UI tests should run headlessly and without user interaction; normal development and CI must not require WSLg or an interactive desktop.
